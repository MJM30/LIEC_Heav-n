Project overview

What LIEC One is for

LIEC One is an education-management application for student records, admissions, PREPA and training management, international student support, administration, documents and education-related finance.

Included

Education operations

Students, admissions, education services, training cohorts, student support, partner requests, documents and administration.

Included

Education finance

Invoices, invoice items, payments, allocations, expenses, refunds and partner-service charges with a traceable history.

Not included

IT consulting

ServiceNow or unrelated IT consulting business operations are outside this application's scope.

Current state

Prototype, not production

The current HTML screens are a browser demo. Real authentication, database connections, secure document storage, email delivery and partner APIs still need implementation.

Global UI rules

Design & branding corrections

  • Use the supplied LIEC logo and preserve its proportions; show the LIEC One wordmark with LIEC in green and One in blue.
  • Use a modern, clean, responsive light interface with white surfaces and soft cyan, blue, turquoise, lime and yellow accents.
  • Use Arial throughout with a 12px base font size for the application interface; allow larger headings for clear hierarchy.
  • Clicking the logo or LIEC One title in the main application should return the user to the Dashboard.
  • Keep buttons visually differentiated: “Add a task” uses a light-blue treatment; “New student” uses a yellow treatment.
  • Make layouts responsive for desktop, tablet and mobile.
Front-end correction

Login page

Keep the original branding/background section and its original visual design. Do not replace it with a plain or unrelated background.

  • Maintain the original two-column composition, with the branding/background section retained on the left.
  • Make the email/password login area slightly larger than the original version by widening its panel/card and increasing internal spacing, while preserving the overall split and balance.
  • Keep the LIEC logo and green/blue wordmark visible.
  • Use the welcome copy: “Helping students build their future.”
  • Use separate wording for the two entities: “LIEC education consulting and PREPA training management”. Do not combine “LIEC-France PREPA” as if it were one entity.
  • Show the product features: student records and admissions tracking; LIEC education consulting and PREPA training management; international services and partner requests.
  • Keep the page responsive. On narrow screens, stack the sections without clipping form controls.
Important: the login page is currently visual only. Implement real authentication server-side, secure session handling, logout, password reset and rate limiting before production. Never store plain-text passwords in the browser or localStorage.

Front-office interaction standards

  • Use searchable, sortable and paginated tables for record-heavy screens.
  • Include filters for status, assigned staff member, date range and relevant module-specific fields.
  • Use confirmation prompts for destructive actions and display clear success/error feedback.
  • Provide a visible record status and a timestamped activity/history panel on workflow records.
  • Use consistent buttons and terminology; distinguish “Save draft”, “Submit”, “Approve”, “Reject”, “Send” and “Close”.

Operational workflows

Core student and partner-service workflows

Blocked Account Certificate

Staff creates request→Validate student & details→Pending / manual processing→Record partner response→Complete / rejected / needs info
  • Capture the student, request date, provider/partner, required details, status, reference number and timeline.
  • Initial operation may be manual. Keep the design ready for a future partner API adapter, but do not claim an API call was made until configured and verified.
  • For future API integration, use server-side credentials, idempotency, retries, redacted request/response logs and error handling.

Accommodation Proof

Create request→Validate details→Draft partner email→Explicit send action→Track reply & outcome
  • Store the partner contact, requested dates/location, student link, status and correspondence history.
  • Initially, record requests locally or manually. Sending email requires a configured transactional email provider and confirmed partner recipient.
  • Track queued, sent, failed, acknowledged and completed states where applicable; do not mark an email sent unless the provider confirms it.

These services support a student's visa preparation process. Do not state that either document is universally required or guarantees visa approval; requirements vary by case and authority.

Finance workflow

Create invoice→Add line items→Record payment→Allocate payment→Reconcile balance
  • Represent invoice items, payments and allocations separately so partial payments and multiple invoices can be handled correctly.
  • Track whether money is paid to LIEC or a partner, and record the recipient, currency, reference and supporting evidence when applicable.
  • Support expenses, refunds and partner-service charges with permission checks and audit history.
  • Use database transactions to prevent duplicate allocations, over-allocation and inconsistent invoice balances.
  • Do not assume the commercial arrangement for partner payments; confirm whether students pay LIEC, the partner, or either, then configure the flow accordingly.
Back office

Backend services & administration

Authentication

Login/logout, password reset, secure password hashing, session expiry, rate limiting, optional MFA and account lockout controls.

Authorization

Server-side RBAC plus record-level checks. Keep finance, settings, sensitive student data and documents least-privilege by default.

API/service layer

Validate all inputs, enforce business rules, return consistent error formats, log correlation IDs and avoid trusting client-provided roles.

Document service

Private object storage, access-controlled uploads/downloads, file type/size checks, malware scanning where available, short-lived signed URLs.

Email service

Transactional provider plus durable outbox, delivery/error status, retry handling and message templates. Keep secrets server-side.

Partner integrations

Adapter pattern for future blocked-account provider API. Configure only after official API documentation, credentials and test environment are available.

Audit log

Record actor, action, entity, timestamp, outcome and safe change metadata for sensitive actions. Never log passwords, tokens or full payment secrets.

Operations

Backups and restore tests, monitoring, migrations, error alerting, environment separation and documented incident response.

Suggested stack

  • Frontend: Next.js + TypeScript + Tailwind CSS (or adapt the existing static HTML into reusable components).
  • Backend: server-side API routes or a dedicated service layer; never connect a browser directly to MySQL.
  • Database: MySQL 8.4 LTS, InnoDB, utf8mb4, foreign keys, indexes and transactions.
  • Money: DECIMAL columns, never floating-point numbers; define currency explicitly.
  • Files: private object storage; database stores metadata and secure storage keys, not public file URLs.

Production readiness

Security, privacy & compliance

  • Enforce authorization in the backend for every route, record, report, export and document download.
  • Use HTTPS, secure cookies, CSRF protection where applicable, output escaping and protection against injection.
  • Validate and normalize all user inputs on the server. Apply upload size/type limits and secure file handling.
  • Keep API keys, database passwords and email credentials in a secrets manager/environment configuration, never in HTML or client-side JavaScript.
  • Minimize personal data collection. Define lawful purpose, privacy notices, retention periods, deletion/correction process and access logging in line with applicable GDPR obligations.
  • Use test data in development. Do not enter real passports, bank details or sensitive student records into the current localStorage demo.
  • Back up the database and files, test restoration, monitor failures and document incident response.
  • Review finance, accounting, contract and data-protection obligations with appropriate professionals before go-live.
Recommended order

Implementation checklist

  1. Freeze interface requirements: approve logo, palette, Arial typography, original login background, enlarged login panel, navigation and role-specific visibility.
  2. Set up the application: create Next.js/TypeScript project structure, reusable layout/components, environment configuration and staging environment.
  3. Build identity and RBAC first: implement real authentication, server-side permissions and automated permission tests before sensitive modules.
  4. Connect the database: review schema, create migrations, seed non-sensitive test data, add indexes and backups.
  5. Implement student and admissions modules: forms, search, validation, status history and assignment rules.
  6. Implement PREPA & Training: cohorts, enrolments, attendance and progress tracking; keep entity naming distinct from LIEC.
  7. Implement service requests: manual blocked-account workflow first; accommodation request tracking and email outbox after provider configuration.
  8. Implement finance safely: invoices, items, payments, allocations, expenses, refunds, partner charges and reconciliation with transaction tests.
  9. Add documents, reports and settings: private storage, permission-aware exports, audit trail and admin-only configuration.
  10. Test before launch: responsive/browser tests, accessibility checks, permission matrix, finance edge cases, backup restore, email failure and API retry scenarios.
  11. Deploy: configure production database, secrets, HTTPS, monitoring, backups, logging, support ownership and rollback plan.
Definition of done: a screen is production-ready only when its backend endpoint, database persistence, validation, permission enforcement, audit trail and failure states are implemented—not merely when the HTML looks correct.
